# Daily Update — August 17, 2026

*Written for non-technical stakeholders. Plain language, no jargon.*

## In one line

The server ran out of disk space. **No client data was lost or damaged** — but
the automatic daily backup had been failing quietly since August 10th, so for a
week there was no fresh copy to fall back on. The cause is fixed, and the same
failure can no longer hide.

---

## What happened

The server's disk reached 100% full. Not "nearly full" — zero bytes left.

The first thing checked was the database itself, because a full disk is exactly
what corrupted it in July. **It is intact.** The integrity check came back
clean, all the records are there, and the hourly refreshes from Monday.com have
been running normally throughout. Nothing anyone did in the dashboard was lost.

The real damage was quieter. The nightly backup needs room to write a copy of
the database; on a full disk it fails. It had been failing every morning since
**August 10th**. The most recent safe copy of the system is therefore a week
old. Nothing bad came of it — but for that week, the safety net had a hole in
it and nobody knew.

---

## Why it could not fix itself

The system is supposed to delete old backups automatically, keeping only the
most recent few. That cleanup worked — but it ran as the *last step* of the
backup routine, after writing the new copy.

So when the disk filled, the backup failed, and the cleanup never got a chance
to run. The one condition that makes deleting old backups urgent was the same
condition preventing it. Every morning it tried, failed at the same point, and
left the disk exactly as full as it found it.

That is now reordered: the cleanup runs whether the backup succeeds or not, so
a full disk frees itself for the next attempt.

Two other things were adding to the pile:

- **Snapshots taken before each software upgrade were never deleted.** Each is a
  complete copy of the database, and four had accumulated since July. Nothing in
  the system had ever removed one. They are now kept to the two most recent.
- **The backup routine now refuses to start if the disk is nearly full**, rather
  than writing half a file. That matters for a reason worth naming below.

---

## One thing that should not have happened

Backups are encrypted, so that a copy of the file is useless to anyone who
obtains it. The encryption step works by writing an encrypted version and then
deleting the original — and it only deletes the original if it finished.

On August 10th it ran out of room partway through. The encrypted version was
never completed, and **the unencrypted original was left on the server**: a
1.5 GB file containing client information, sitting in plain form, produced by
the very routine meant to protect it.

It has not left the server and was not reachable from the internet. But it
should not have existed, and the fix above — refusing to start on a full disk —
is what prevents that specific outcome from recurring.

---

## The system said it was fine the whole time

There is a status check the server exposes so we can confirm it is alive. For
this entire week it answered "everything is fine", because all it did was ask
the database a trivial question and see that it replied.

It now reports whether the disk is healthy, low, or critical. The tooling had
been able to measure this all along — it simply was never part of the check
anyone or anything actually looked at.

---

## An honest note on the diagnosis

The first explanation given for this was wrong. It pointed at a real flaw in how
old backups are matched by name, and that flaw was worth fixing — but it is in a
part of the system that does not write the daily backups, so it was not what
filled the disk. Reading the actual code path that runs in production produced
the real answer, which turned out to be the ordering problem described above.

Recorded because acting on the first plausible cause would have meant deleting
files, believing it fixed, and watching the disk fill again in two weeks.

---

## Some good news, while we were in there

The write-back problem from August 7th — status changes not reaching Monday.com
— **has stayed fixed**. There are twelve failed writes sitting in the queue, and
every one of them predates that repair; the newest is from hours before it went
live. Ten days, zero new failures.

Those twelve are the changes that were lost during the original problem. They
cannot be replayed safely now — they would overwrite whatever has been set in
Monday since — but the record of *what* was attempted, on which case, by whom,
is intact, so it can be turned into a list for the people who made them.

---

## Where things stand tonight

- **The database is verified healthy.** No data loss, no corruption.
- **The fixes are written and tested but not yet deployed.**
- **Still to do on the server:** finish clearing old backup files, confirm one
  setting that may still be holding far more daily backups than intended, and
  take a fresh backup — closing the week-long gap is the most urgent item on
  this page.
- **One follow-up:** the unencrypted copy from August 10th is currently the
  newest restore point, so it should be encrypted rather than simply deleted.

---

## Closing note

Nothing was lost this week, and that is worth saying first. What was lost was
*certainty* — for seven days the system had no fresh way back if something had
gone wrong, and every signal available said it was healthy.

The same shape keeps recurring: in July a full disk corrupted the database, on
the 7th a write path reported success while doing nothing, and this week a
backup that had stopped running looked identical to one that was working. Each
time the failure was measurable well before it mattered, and nothing was
measuring it. Rather more of today's work went into the measuring than into the
fixing, and that is the right ratio.
