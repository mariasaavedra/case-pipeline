# Daily Update — September 3–4, 2026

*Written for non-technical stakeholders. Plain language, no jargon.*

## In one line

The automation that creates a consultation folder for every new client is
**live** — replacing the Zapier workflow that broke — and the backlog of the
last 45 days has been cleared. Along the way, two problems came to light that
had nothing to do with consult folders, one of them affecting our ability to
restore the database if we ever needed to.

---

## The consult folder automation is running

When a client books a consultation through Calendly and that consultation
actually takes place, they need a folder in SharePoint. This used to happen
automatically through Zapier. It broke — Zapier lost the ability to recognise a
folder that already existed, so it either failed or created duplicates.

The replacement is now switched on. Every two hours during the working day it
looks at recent consultations and, for each one:

- **Finds the folder if it already exists**, checking the most advanced location
  first. A client who has already hired the firm, or whose case has closed, must
  never be given a fresh "consultation" folder alongside their real case file.
- **Creates one only if there genuinely isn't one**, and records the link back
  on the client's profile.
- **Leaves cancellations, no-shows and upcoming appointments alone.** They have
  not consulted yet, so they get nothing.

Once the consultation has happened, it also writes a **Consultation Summary**
document into the folder — the client's details, the reason they booked, and the
attorney's note.

### Clearing the backlog

Before switching it on, we ran it in preview mode over the last 45 days — 226
consultations. It reported exactly what it would do without touching anything.

The result was reassuring: **203 of the 226 needed nothing at all.** Their
folders already existed and were already recorded. That is what a safe
automation looks like — it should almost always find there is nothing to do.

The remaining 23 were then processed for real:

| | |
|---|---|
| Folders created | 9 |
| Existing folders found and linked | 14 |
| Consultation Summary documents written | 1 |
| Failures | 0 |

Running it again afterwards found **nothing left to do** — which is the proof
that it finished cleanly and won't repeat its own work.

## Four client names needed a person to look at them

This was the part that genuinely needed human judgment, and it is worth
explaining because it will come up again.

A folder is named from the client's first and last name. If those are recorded
oddly, the automation doesn't fail — it quietly creates a correctly-formatted
folder in the *wrong place*, sitting next to the client's real one where nobody
thinks to look. So the preview run was reviewed by eye before anything was
written.

Four names looked wrong. Three were corrected in Monday.com first:

- One client had her **paternal surname recorded inside her first name**, so
  only her second surname was being used. She would have been filed under the
  wrong letter entirely. Now filed correctly.
- One had a **stray character in the first name** and an **unusual accent** on
  the surname that no other record in the system uses — which would have started
  a second spelling of a common surname.
- One had a first name in **all capitals** where every neighbouring folder uses
  normal capitalisation.

The fourth turned out to be **correct as recorded** — an unusual-looking first
name that is simply the client's name, confirmed against his documents. It was
left alone.

The lesson worth keeping: the automation is deliberately built to *refuse* a
name it cannot make sense of rather than guess at one. About 3% of consultations
fall into that category and will always need a person. That is by design — a
name on a report costs somebody a minute, a wrong folder costs a cleanup nobody
realises is needed.

## A scheduling bug caught before it mattered

The automation was set to run "during the working day, 7am to 7pm". It would
actually have run **2:30am to 2:30pm** — the server keeps time in a different
zone from the firm, and nothing had told the schedule which one to use.

Nothing would have looked broken. Folders would still have appeared. But a
consultation finishing at 3pm would have waited until the small hours for its
folder, which is exactly the promptness the automation exists to provide.

This is the second time this particular confusion has caused a bug here — the
first was call times being recorded five hours off. The fix names the firm's
time zone in one shared place so there isn't a third.

## The more serious find: a backup that would not have worked

While checking the server, one of the daily database backups from **September
2nd** turned out to be **incomplete**. The encryption of that backup stopped
about two thirds of the way through and never finished.

Two things went wrong at once:

1. **The backup file is unusable.** It has a perfectly normal name and sits in
   the list of saved backups, so the system counted it as one of the four
   restore points we keep. In practice we have had **three working backups while
   believing we had four** — and we would only have discovered that at the
   moment we actually needed to restore something.

2. **An unencrypted copy of the database was left behind.** Because the
   encryption never completed, the original plain copy was never cleaned up. It
   contains every client record, unprotected, and has been sitting on the server
   since September 2nd.

**To be clear about the risk:** the server itself is not known to have been
accessed by anyone unauthorised, and the file is not reachable from the
internet. This is a problem to fix promptly, not an emergency.

The fix, written today, is simple. A completed encrypted backup is always
exactly a fixed amount larger than the original — so the system now **checks the
size before deleting the original**, and if anything went wrong it discards both
pieces rather than leaving a half-finished backup that looks real. The next
scheduled run then tries again.

Two things still outstanding:

- **The leftover unencrypted file should be deleted.** It is redundant — a good
  encrypted copy of that same day exists. Awaiting the go-ahead.
- **Nothing yet detects an already-damaged backup.** Today's fix prevents new
  ones; a periodic check of the existing backups is the sensible follow-up.

Also cleaned up: 550 tiny leftover files that had accumulated in the backup
folder since July because nothing ever removed them. Harmless in size, but they
are clutter in the one folder someone would be searching during an emergency.
