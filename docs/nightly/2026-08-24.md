# Daily Update — August 24, 2026

*Written for non-technical stakeholders. Plain language, no jargon.*

## In one line

Every time anyone opened the dashboard, their browser was downloading about five
times more than it needed to — and the server was sending all of it in full
rather than compressed. Three fixes, measured rather than guessed, bring a first
load from roughly 736 KB down to about 150 KB. **Nothing is deployed yet**; the
changes are written, tested and waiting.

---

## What was actually slow

Nobody reported this. It came out of checking the dashboard against a published
list of the things a web application is supposed to get right, one item at a
time. Most of the list we already passed. Three items we did not, and all three
were in how files travel from the server to your browser rather than in the
dashboard itself.

**Compression was switched off.** The software that serves the dashboard can
compress everything it sends — the same idea as zipping a folder before emailing
it — and it arrives at the browser, unzips instantly, and nobody notices
anything except that it was faster. This is standard. It ships turned off by
default, and we had never turned it on. So every file, every page, and every
list of cases went out at full size. The heaviest thing the dashboard asks for
is a week of appointments: 312 KB uncompressed, 46 KB compressed. We were
sending the 312.

**Everything loaded at once.** All the dashboard's screens — Settings,
Appointments, the client detail view, the calendar — were packed into a single
file that had to arrive before anything at all appeared. Opening the dashboard
to glance at today's deadlines meant downloading the Settings screen you were
not going to open. Those screens are now fetched only when someone actually
navigates to them.

**The fonts took a detour.** The dashboard's typefaces were being fetched from
Google's servers. Before a single letter could start downloading, the browser
had to look up a second company's address, negotiate a secure connection to it,
and wait for a reply — all while the page sat blank. The fonts now come from our
own server, alongside everything else.

---

## What this actually changes

| | Before | After |
|---|---|---|
| Downloaded on first visit | ~736 KB | ~150 KB |

The difference is most noticeable on a slow or mobile connection, and on the
first visit of the day before anything is cached. It is not a redesign and
nothing looks different — the same dashboard simply starts sooner.

There is a second benefit that will not be visible but matters: the compression
fix applies to the case data itself, not just to the dashboard's code. Every
list of appointments, every client summary, every search result now travels
compressed. That is less work for the server on every request anyone makes.

Each of these was verified rather than assumed — the compression tested against
a real copy of the running setup, the loading behaviour watched in an actual
browser, and the full test suite (628 tests) run before and after.

---

## An honest note on one of the claims

When these three problems were first written up, the font issue was described as
wasting about 60 KB on every load, because the dashboard was requesting an
italic version of a typeface that nothing in it uses.

That was overstated. Browsers only download a typeface they actually need to
draw something with, so that italic version was very likely never fetched at
all. Removing it is still correct — it was declared for no reason — but the real
benefit of the font work is the detour described above, not the 60 KB.

Recorded because the number had already been put in writing, and a fix is worth
less if the reason given for it does not hold up.

## A near miss worth naming

The calendar feature currently being built is unfinished and shares a file with
this work. Committing the performance changes without noticing that would have
sent a half-finished calendar toward production, and would have failed the
automated build outright — meaning the whole thing would have silently not
deployed.

Worse, an earlier check had already claimed the two sets of changes were cleanly
separated. That check was wrong: it filtered the comparison in a way that hid
exactly the lines that overlapped. The mistake was caught by looking again
before committing rather than by anything automatic.

The commit now contains only the performance work. The calendar work is
untouched and still in progress.

## Two small things, while we were in there

- **The dashboard had no icon.** Every single page load asked the server for one
  and got an error back. It has one now — the small navy square in the browser
  tab.
- **A duplicate file was deleted.** There were two copies of the dashboard's
  starting page, one of which the build has ignored since the project was
  restructured months ago. They were identical, so it never mattered; this
  week's font change made them differ, which is exactly how someone ends up
  editing the copy that does nothing. This is the same trap as a past incident
  where a fix appeared not to take effect.

## Where things stand tonight

- **The work is committed and tested but not deployed.** It is waiting for
  review and merge, after which the images build automatically and the server
  needs one command run on it.
- **Nothing about it is risky to hold.** These are delivery improvements; no
  case data, no Monday.com behaviour, and no screens were touched.
- **One question is still open, and it is the more important one.** The security
  review this came out of flags encrypted connections as its highest priority
  item, and nothing in the project's own configuration sets one up. It is
  entirely possible that something outside the project provides it — that is a
  normal arrangement and would need no change. But it has not been confirmed
  either way, and until it is, it should not be assumed. That is worth answering
  before anything on this page.

---

## Closing note

None of today's three problems were bugs. Nothing was broken, nothing was
failing, and nobody had complained — the dashboard worked correctly the whole
time while doing several times more work than it needed to on every visit. Two
of the three were settings that ship switched off and had simply never been
switched on.

That is a different failure mode from the ones on recent pages here, where
something was quietly broken and no measurement was watching. This time the
measurement had never been taken at all. It took an afternoon and produced a
five-fold difference, which mostly says it should have been taken much earlier.
