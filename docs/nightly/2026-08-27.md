# Daily Update — August 27, 2026

*Written for non-technical stakeholders. Plain language, no jargon.*

## In one line

No new features today — instead, a full top-to-bottom review of the system's
health, the kind you do periodically to catch problems before they find you.
The results are reassuring: everything protecting client data held up under
scrutiny. The review turned up one real bug, which was fixed and covered by a

---

## What was reviewed

Think of this as an inspection rather than construction. The whole codebase —
roughly 50,000 lines across the dashboard, the server, and the sync engine —
was checked for security holes, correctness bugs, and the kind of structural
wear that makes future changes risky.

**The things that matter most came back clean:**

- **Sign-in cannot be faked or bypassed.** Every route that touches client data
  verifies the user's Microsoft sign-in against Microsoft directly, and
  separately confirms the account is still active — so an employee who leaves is
  locked out immediately, even if their sign-in hasn't expired yet.
- **No way found to trick the database into leaking data.** This is the single
  most common way applications get breached. Every place where a user's input
  reaches the database was checked individually; all of them handle it safely.
- **Stored passwords and connection keys are encrypted**, with separate keys for
  the app and for backups — so a compromise of one doesn't expose the other.
- **The dashboard can't be used to attack the people viewing it**, and sign-in
  sessions are stored in the safer of the two available places.
- **Shutdowns are clean.** When the server restarts or is redeployed, the
  database is closed properly rather than mid-write — which is what protects
  against the kind of corruption that hit us in July.

**Also confirmed working:** the automated checks all pass, and the system
builds correctly from a clean slate.

## The bug that was found, and fixed

Yesterday's "tag a coworker in a note" feature works — but it had a gap in one
specific situation.

When a call is logged, the note goes to Monday.com immediately. If Monday.com
happens to be **down** at that exact moment, the app doesn't lose the note: it
holds onto it and retries automatically once Monday is back. That safety net has
been in place for a while and works well.

The gap: on that retry path, the note was going out **without the coworker tag**.
The note itself would arrive correctly and nothing would look wrong — but the
person tagged would simply never be notified, and no one would have any way to
know. The tag would just quietly evaporate.

**To be clear about the impact: there's no evidence this affected anyone.** It
only triggers if Monday.com is down at the precise moment someone logs a call
*and* tags a colleague in it — a narrow overlap that we have no record of
happening. This was caught by reading the code, not by anyone hitting it. That's
the point of doing a review like this: finding the problem before it costs
someone a missed message.

It's now fixed, and covered by a test written specifically for this failure. The
test was verified to actually work by deliberately re-breaking the code and
confirming the test caught it — a test that passes whether or not the bug is
present protects nothing.

While in there, one piece of intentional behavior that looked like a mistake was
documented: tagging someone notifies them **once**, on the call entry. The note
also gets mirrored onto the client's profile, but deliberately without repeating
the tag — otherwise one note would ping the same person twice.

## A safety net added

Until today, the automated checks that run before any change could ship verified
that the code was correct, but never actually confirmed the app still *builds*.
That meant a change that broke the dashboard's build would only reveal itself
later, after it had already been merged.

That check is now part of the pre-merge process. It's one line, and it closes a
gap that was well-positioned to waste an afternoon someday.

## About "4 high-severity vulnerabilities"

The standard security scan for outside software we depend on reports four
high-severity items. This needs context, because the headline is misleading.

Two of them are in a spreadsheet component, and both only apply when *reading*
spreadsheet files from an untrusted source. This app never does that — it only
*writes* spreadsheets, from our own data. The vulnerability has no path to reach
us. The other two are in build-time tooling that never runs on the live server,
and a routine update clears them.

None of the four are actionable emergencies. Worth knowing precisely, so that a
scary-sounding scan report doesn't cause a fire drill later.

## Maintenance items worth planning for

These are not urgent and nothing is broken. They're the kind of thing that gets
harder to fix the longer it waits.

- **There's no automated style checker.** Most projects run a tool that flags
  sloppy or risky patterns as code is written. This project has never had one.
  Adding it is low-risk and mostly prevents *future* problems.
- **One file has grown to 2,115 lines** and holds far more than it should. The
  rest of the system is well-organized; this one file didn't get the same
  treatment as it grew.
- **The write operations in that file have no automated tests.** Reading data is
  well tested. Creating and editing — logging a call, posting a note, changing a
  status — is not. This is the most important of the three, because it's where a
  mistake would touch real client records.

The recommended order is deliberate: **tests before reorganizing.** Splitting up
a large file without tests underneath it is exactly the kind of change that looks
successful, passes every check, and surfaces a problem weeks later in real data.
