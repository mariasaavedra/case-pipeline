# Daily Update — July 24, 2026

*Written for non-technical stakeholders. Plain language, no jargon.*

## In one line

The site went down this morning with a "Bad Gateway" error; it was restored from
a verified backup and is back up with **more** data than before. Separately, the
Contracts tab was rebuilt into a payment history, and contract statuses now read
in plain "where is this case" terms.

---

## The outage, and how it was handled

**What happened.** The site came up this morning showing "Bad Gateway." The cause
was that the live database file on the server had become **corrupted** — damaged
in a spot that day-to-day use never touched, so the app had been running fine for
days without anyone noticing. The corruption only surfaced when the app tried to
read the whole file end-to-end, which put it into a restart loop and took the site
offline.

**How it was fixed.** We restored from a backup — but not the server's own, because
the corruption turned out to predate the server's most recent daily backups. We
used a **verified-clean local copy** instead, which was also **more complete** (it
carried the full email/notes history the server had never finished importing). The
damaged file was set aside (not deleted) in case we want to examine it, and the
site came back healthy.

**Where things stand.** The site is up, the data passed an integrity check, and it
now includes ~125,000 email/activity entries it didn't have before. The automatic
overnight refresh remains **switched off** on purpose (see below).

**Honest note.** Re-enabling the automatic sync the night before is what surfaced
this. The corruption itself most likely came from the *old* refresh design (the
one that deleted everything before re-downloading), but turning the schedule back
on is what tripped over it. Two things are now on the must-do list before any
automatic sync runs again: (1) find the exact cause of the corruption, and
(2) make the database more resilient so a bad refresh can't damage it. Until then,
refreshes are run by hand where someone can watch.

## Contracts: a real payment history

The Contracts tab was a simple list. It's now a **table of the client's contract
payments**:

- every contract, with the **AF and PF amounts** on it,
- the actual **Open Form or Court Case** each contract represents, and that case's
  **current status**,
- a **paid-to-date total** at the bottom,
- and unpaid or pending contracts listed too, shown in a lighter shade.

The linked case is looked up live. On the current data, about **6 in 10** contracts
resolve to their case; the rest simply show "not linked," which is honest — many
contracts in Monday were never linked to a case.

---

## Contract statuses now read in case terms

Some Monday statuses make sense for the daily fee-K workflow but not for
understanding where a case actually is. These now **translate** in the client view:

- **"Create Project" now reads as "Completed" (green).** It means the contracting
  is done — paid, e-file created — so it should not sit in the "pending" pile.

This fixed a real bug along the way: the old rule for "which contracts are finished"
used labels that **don't exist** in the real Monday workspace, so **1,165 completed
contracts were being shown as still-active**. They're now correctly filed as done.

The specific translations live in one editable list, so the wording and colors can
be tuned without code changes.

## What's next

- **Root-cause the corruption and harden the database** before switching automatic
  refreshes back on.
- Server tidy-up: clear the junk files left by this morning's restart loop, and
  reduce how many backups are kept.
- Both of today's contract changes are on `main` and take effect on the next
  deploy — which should be watched, since it's the first deploy since the restore.
