# Daily Update — August 7, 2026

*Written for non-technical stakeholders. Plain language, no jargon.*

## In one line

Status changes and notes had not been reaching Monday.com for anyone who
connected their Monday account before August 4th — the dashboard showed them as
saved and then quietly reverted them. Found, fixed and deployed today, along
with a rebuilt set of filters on the client timeline and two changes that make
this kind of silent failure harder to repeat.

---

## What was actually happening

When you change a status here, the dashboard sends that change to Monday under
**your** Monday account, so the change is attributed to you rather than to a
faceless service account. That connection is made once, from Settings.

Monday grants that connection a fixed set of permissions **at the moment you
connect it**, and never widens them afterwards. Permission to edit a field was
added to our connection screen on **August 4th**. So every account connected
before that date was allowed to post notes and nothing else — and one connected
on June 30th, during a short window, could not even do that.

Three things then combined to hide it:

1. The dashboard applied your change locally straight away, so on screen it
   looked like it had worked.
2. When Monday refused the change, the system filed it for a retry — and every
   retry used the same connection Monday had just refused. After five attempts
   it gave up.
3. A while later the routine refresh pulled Monday's real value back over yours,
   so the status simply appeared to change back on its own.

Nothing announced a failure at any point. The admin screen reported a number of
stuck changes but not the reason, which is why the pattern was not obvious
sooner.

---

## The fix

- **Changes now go through even from an out-of-date connection.** If Monday
  refuses your personal connection, the change is made under the firm's shared
  account instead. You lose your name on that one change; you do not lose the
  change. That tradeoff is deliberate.
- **You get told.** An out-of-date connection now turns the Monday panel in
  Settings amber and says so. Reconnecting is one click and puts your name back
  on future changes.
- **The retry queue stopped being pointless.** It now falls back the same way,
  instead of spending five attempts on a connection that cannot work.
- **Admins can see the reason.** Sync Health lists recent failed write-backs
  with Monday's own error message, not just a count.

A dead duplicate entry was also removed from the server configuration file. It
was harmless where it sat, but had it been read in the other order it would have
broken *every* write for everyone, not just the ones described here.

---

## What this does not fix

**Changes lost over the past days are gone and need to be redone.** They were
never applied in Monday, and replaying them now would be worse than not: they
would overwrite whatever has been set in Monday since. Anyone who changed a
status and later found it back to its old value should assume the change did not
take.

The window depends on the account:

- Connected on **June 30th** — notes and status changes both affected.
- Connected between **July 1st and August 4th** — status and field changes
  affected; notes were fine.
- Connected on or after **August 4th** — unaffected.

---

## The timeline filters on a client's page were rebuilt

Unrelated to the outage, and the change people will actually notice.

The row of filters above a client's timeline had seven buttons — Notes, Emails,
Activities, Documents, Notices/RFEs, Appointments — plus a "Last 30 days"
toggle. **"Notes" was lying.** It showed notes written directly on a client, but
hid the ones written on a document or against an appointment. So the button
named after the thing you were looking for was the one that hid it.

It is now two buttons, **All** and **Notes**, where Notes means *everything that
isn't an email*. That is a rule you can predict from the label, and it can't
quietly omit a category again — anything new arriving from Monday appears under
Notes by default rather than falling into a gap.

The 30-day toggle became a proper period: **All time / 30 days / 90 days / 12
months**, plus a date range for "what happened in March". The old toggle also
had a subtler fault — on a client with a busy inbox it filtered only the most
recent page of entries, so an older period could come back empty while the
entries existed. The period is now applied before the page is cut.

More filters can be added over time, as discussed. This was the foundation, not
the finished set.

---

## The same mistake can no longer hide

Today's outage and the June 30th one were both a configuration value that was
wrong in a way that produced no error. That is now checked when the system
starts: duplicated settings, values still left as their example placeholder, a
malformed Monday token, an address pointing at a developer's machine instead of
the live server, a schedule written in a way that means "never run".

**If any of those is wrong, the system now refuses to start** rather than
starting and behaving strangely. That is a deliberate trade: a failed start is
loud, immediate, and gets fixed in minutes. What we had instead was a fault that
ran for days.

It never writes any password or token into a log — only the name of the setting
and what is wrong with its shape.

---

## Groundwork for "who did what"

The system has quietly kept a record of every change made through the dashboard
for some time — who changed which status, who posted which note, who generated
which document. Two things made that record hard to use, and both are fixed.

It now identifies each record by something permanent. Previously it pointed at
an internal reference that the nightly refresh regenerates, so a record written
on Monday no longer resolved to anything by Tuesday — the entry survived, but
what it referred to did not. **The records already written were recovered**, not
written off: the permanent reference had been stored alongside them all along.

And it can now be asked questions: what did one person do, everything that ever
happened to one case, everything in a date range.

This is groundwork rather than a feature — nothing new is visible yet. It is
what a per-person daily summary would be built on.

---

## Where things stand tonight

- **Deployed and verified.** Everything above, plus yesterday's four fixes, is
  live. The system is reporting healthy and running the exact version that was
  reviewed.
- **The one thing still needing a person:** anyone who connected their Monday
  account before August 4th should reconnect it once, from Settings. Their
  changes are being saved either way — under the firm's shared account instead
  of their name until they do.
- **Yesterday's loose end turned out to be already done.** Monday did not need
  re-registering for deleted notes after all; checking showed all nineteen
  boards already subscribed.

---

## Closing note

The uncomfortable part of today is not the bug — it is that the system reported
success while doing nothing, for days, and the one screen built to show trouble
showed a number without a reason. The fix restores the writes; the more useful
change is that a refusal is now visible to the person it affects, at the moment
it affects them.

The rest of the day turned out to be the same theme in three other places. A
filter button that hid the very thing it was named after. A configuration
setting that was wrong without complaining. A record of changes that stopped
pointing at anything overnight. None of these announced itself either — each was
found by going and looking.

That is the pattern worth naming: the failures that cost the most here are not
the ones that break loudly. They are the ones that keep reporting that
everything is fine.
